# ADR-26102002: Guard affiliation-scope на публичных SaaS

## Статус

✅ **Принято**

## Контекст

[Git Herder][product-intent-readme] при [SCM-отборе][repository-selection] получает
набор репозиториев через перечисление API и оценивает критерии локально
([ADR-26102001][adr-local-eval]). Перечисление всегда ограничено **scope** на стороне
платформы: адаптер не может вернуть больше, чем позволяет выбранный контур запросов.

На хостах **`github.com`** и **`gitlab.com`** каталог **общедоступных** репозиториев
настолько велик, что:

- одним запросом (или серией без жёсткого scope) получить и обработать «весь
  каталог» непрактично по объёму, квотам API и времени;
- неявно широкий отбор без привязки к пользователю создаёт риск бессмысленных
  массовых операций.

На **self-hosted** GitLab, GitHub Enterprise Server и иных инстансах масштаб каталога
обычно иной; отдельный guard для публичных SaaS не должен мешать полному перечислению
в пределах доступа пользователя на инстансе.

Перечисление — через SCM-адаптеры ([ADR-26101703][adr-http]); устойчивость массовых
сетевых шагов — [resilient-network][resilient-network].

## Решение

Если в [профиле][profiles] SCM-хост после нормализации — **в точности** `github.com`
или `gitlab.com`:

- к **любому** SCM-отбору **неявно** добавляется ограничение scope перечисления:
  только репозитории **«связанные с текущим пользователем»** (участие, доступ,
  affiliation — **семантика задаётся в адаптере** платформы, не именами эндпоинтов
  в этом ADR);
- ограничение действует **даже если** пользователь не задал его явно в параметрах
  отбора;
- после перечисления в этом scope критерии отбора по-прежнему оцениваются локально
  ([ADR-26102001][adr-local-eval]).

На хостах, отличных от `github.com` / `gitlab.com`, этот guard **не** включается.

## Параметр `scope` на публичном SaaS {#scope-public-saas}

Прикладной контракт значений `affiliated` \| `all` для `--scope` — в спецификации
SCM-отбора (hub); маппинг на API конкретного `upstream` — в
`repository-listing/` (файл `scope.md`) этого `upstream`.
**Ниже — единые правила только для хостов `github.com` и `gitlab.com`** (hostname
после резолва [профиля][profiles] **в точности**, как в решении выше). На других
хостах этот раздел **не** применяется; guard из решения выше на них **не**
включается.

Режим **`--q*`**, не `--scm-search`:

| `scope` после резолва | Поведение на `github.com` / `gitlab.com` |
| --------------------- | ---------------------------------------- |
| `affiliated` (в т.ч. default) | Ограничение перечисления **согласовано** с guard из решения выше (репозитории, связанные с текущим пользователем). Явный `affiliated` **не** расширяет scope шире guard. |
| `all` | Ограничение affiliation из guard **не** добавляется к запросам перечисления и обогащения (явный opt-out). |

Перед перечислением при `scope=all` на `github.com` или `gitlab.com` **без**
`--scm-search` обязательны:

- запись `level=warn` в журнал выполнения;
- то же предупреждение на консоль (pterm), по тому же принципу, что предупреждения
  при управлении профилями в спецификации продукта.

Если задан `--scm-search`: предупреждение по этому разделу **не** выводится;
`scope` к запросу в SCM **не** применяется (контракт hub).

Реализация на REST (membership, involves и т.д.) **не** дублируется здесь — только
в `repository-listing/scope.md` соответствующего `upstream` (листинг, не enrichment).

## Аргументация

| Альтернатива | Почему не выбрана |
| ------------ | ----------------- |
| Полный каталог публичных репо на `github.com` / `gitlab.com` | Нереализуемо и бессмысленно по объёму и квотам API |
| Требовать явный org/group на SaaS вместо implicit scope | Плохой UX; не снимает риск слишком широкого неявного отбора |
| Тот же guard на GHES и self-hosted GitLab без отдельного решения | Иной масштаб каталога; лишние ограничения на корпоративных инстансах |

## Последствия

### Позитивные

- Отбор на публичных SaaS остаётся в практичном масштабе без ручного указания scope.
- Поведение предсказуемо для типичного [ST-1][st-1]-сценария «мои репозитории на
  github.com / gitlab.com».

### Негативные

- Пользователь не получит «все публичные репо на GitHub» при default `scope=affiliated`;
  расширение — только через явный `scope=all` с предупреждением (см.
  [§ scope на публичном SaaS](#scope-public-saas)).
- Семантика «связан со мной» различается между GitHub и GitLab — адаптеры должны
  документировать различия в спецификации, не в ADR.

### Компромиссы

- Сравнение hostname **строгое** (`github.com`, `gitlab.com`); алиасы и кастомные
  домены SaaS — вне scope без нового ADR.
- Guard задаёт только **scope перечисления**, не заменяет пользовательские критерии
  имени/namespace.
