# ADR-26110301: Политика компонента RetryingQueue

## Статус

⏳ **Предложено**

## Контекст

[Git Herder][product-intent-readme] выполняет **массовые** операции над множеством
однотипных объектов (страницы SCM, карточки репозиториев, позже — локальные
копии и сетевые шаги `git`). Повторы после сбоя и политика «пропустить объект /
остановить прогон» должны быть **единым механизмом**, а не дублироваться в каждой
команде.

[ADR-26101703][adr-http] переносит retry **из** HTTP-транспорта: `net/http` без
встроенных повторов. Capability [отказоустойчивого выполнения][resilient-network]
описывает ожидания продукта к очереди; ранние формулировки capability
акцентировали только **сетевые** сбои — для реализации нужен однозначный контракт
компонента **RetryingQueue** в целевой архитектуре.

Альтернатива «очередь сама классифицирует сеть vs фатальная ошибка» потребовала
бы общего таксономического слоя ошибок во всех обработчиках (HTTP, git, парсинг
ответа SCM) и дублировала бы проверки, которые command flow и так делает **до**
массового прогона.

## Решение

Вводим прикладной компонент **RetryingQueue** (пакет с узким API в одном Go-модуле).

### Контракт

| Вход | Смысл |
| ---- | ----- |
| Множество объектов | Любой тип; очередь не интерпретирует семантику |
| Обработчик | Функция «объект → error»; успех — `nil` |
| `retries-number` | Сколько раз **повторить** после первой ошибки на объекте; `0` — без повторов |
| `on-error` | `abort` или `continue` — политика **после исчерпания** попыток на объекте |

Метод **`Execute`**:

1. Пока очередь не пуста — извлечь объект (`pop`).
2. Вызвать обработчик.
3. При ошибке: если остались повторы — увеличить счётчик попыток для объекта и
   **вернуть объект в конец** очереди; иначе применить `on-error`:
   - **`abort`** — немедленно завершить `Execute` с признаком сбоя;
   - **`continue`** — зафиксировать неуспех объекта и перейти к следующему.
4. Прогресс длительного `Execute` — через компонент терминального UI (pterm только
   там); детали отображения — не в этом ADR.

### Инварианты компонента

- Очередь **не** классифицирует ошибки обработчика (любой `error` подлежит
  повтору, пока не исчерпан лимит).
- Очередь **не** знает про SCM, HTTP и git; только вызов обработчика и политика
  повторов / `abort` / `continue`.
- Один прогон `Execute` — **последовательная** обработка (без пула воркеров в
  этом решении).
- **Backoff** между повторами, параллельность и запись каждой попытки в журнал —
  **не** входят в это решение (остаются открытыми на уровне capability или
  последующих ADR).

### Разделение ответственности

- **Command flow** команды: валидация argv и профиля, синтаксис критериев,
  обязательные параметры — **до** создания очереди.
- **RetryingQueue**: повторы и `abort` / `continue` на объекте после лимита.
- **Код выхода процесса** и агрегация «были ли сбои при `continue`» — у команды,
  не внутри очереди.

Синхронные шаги без повторяемого обработчика (например локальная фильтрация
массива карточек в памяти) **не** оборачиваются в RetryingQueue.

## Аргументация

| Альтернатива | Почему не выбрана |
| ------------ | ----------------- |
| Повтор только «сетевых» ошибок внутри очереди | Дублирование классификации в каждом обработчике; git и HTTP возвращают разные типы сбоев |
| `abort` / `continue` только в command flow после `Execute` | Два места с одной политикой; риск расхождения с глобальными флагами CLI |
| Типизированный результат обработчика (retryable / fatal) | Усложняет API; command flow уже отсекает фатальные ошибки до очереди |
| Параллельные воркеры в P0 | Открытый вопрос capability; сознательно откладываем |

## Последствия

### Позитивные

- Один переиспользуемый пакет для массовых прогонов (`report`, будущие `clone` и
  др.).
- Согласованность с [ADR-26101703][adr-http]: HTTP не повторяет запросы сам.
- Простой контракт для ArchiMate и модульных границ SOLID.

### Негативные

- Ошибка конфигурации, попавшая в обработчик, может быть **повторена** до лимита
  (митигация — валидация до очереди в command flow).
- Без backoff повторы при rate limit могут усугублять нагрузку на SCM (открытый
  вопрос capability).

### Компромиссы

- Универсальность «любой error» вместо точной сетевой таксономии — осознанный
  обмен на единый механизм и меньший объём кода.
