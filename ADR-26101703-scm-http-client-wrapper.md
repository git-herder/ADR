# ADR-26101703: HTTP-клиент для SCM API

## Статус

✅ **Принято**

## Контекст

[Git Herder][product-intent-readme] обращается к [SCM-платформам][scm-platform] по
HTTP API: клонирование с платформы, метаданные, массовые операции. Полный перечень
платформ и их API **заранее не зафиксирован**; со временем появятся SCM без
официальной Go-библиотеки.

Нужен единый способ ходить в API, не привязываясь к одному вендору и не размножая
несовместимые стеки в коде.

Сетевые повторы и устойчивость — отдельная тема ([отказоустойчивое выполнение по
сети][resilient-network]); здесь только транспорт HTTP.

Связанный стек приложения: [ADR-26101701-go-application-stack][adr-stack]. Локальный
git — [ADR-26101702-host-git-from-path][adr-git].

## Решение

Для вызовов SCM API используем **свою обёртку над стандартным `net/http`**.

- Базовый транспорт — **`net/http`** из Go, без стороннего HTTP-клиента «целиком».
- Обёртка задаёт общие правила: базовый URL, заголовки, аутентификация, разбор
  ответов и ошибок на уровне, общем для всех SCM-адаптеров.
- Конкретные платформы (GitLab, GitHub и др.) — **адаптеры** поверх этой обёртки, а
  не отдельные несвязанные HTTP-стеки в каждом модуле.

Официальные клиенты вроде `gitlab.com/gitlab-org/api/client-go` и
`github.com/google/go-github` **сейчас не берём** как основу всего слоя: для части
SCM своей библиотеки не будет, и **всё равно** понадобится общая обёртка. Раньше
строим один контур на `net/http`, чем потом сливать чужие клиенты с разными
моделями.

HTTP-клиенты **со встроенным retry не используем** — обёртки, которые сами переотправляют
HTTP-запросы.

Встроенный retry в HTTP-клиенте **не закрывает** повторы после сетевых сбоев для всего
продукта. Локальные git-операции идут не Go-кодом, а **отдельным процессом `git`**
([ADR-26101702][adr-git]); сеть там трогает сам `git`, на эти запросы наш HTTP-клиент
**не влияет**. Плюс повторять нужно не только «упал HTTP», но и лимиты API, временную
недоступность, шаг массовой операции целиком.

Поэтому retry делаем в **отдельном слое** над операциями (вызов SCM API, запуск `git`,
массовый прогон) — одна политика на все каналы. Раз повторы всё равно не в
транспорте, HTTP-клиент с retry не даёт выгоды: достаточно `net/http` без встроенных
повторов.

Детали политики retry, таймаутов и очереди — в прикладной спецификации и capability
сетевого выполнения, не в этом ADR.

## Аргументация

| Вариант | Почему отказались |
| ------- | ----------------- |
| Только client-go / go-github без общей обёртки | Не масштабируется на SCM без официальной либы; два разных API в коде |
| Сразу тянуть все официальные SDK под каждую платформу | Тот же разнобой; перечень SCM ещё не закрыт |
| resty, go-retryablehttp и аналоги как основной клиент | Retry только в HTTP; не покрывает сеть внутри процесса `git`; единая политика повторов всё равно нужна снаружи |
| Полный отказ от `net/http` (только gRPC и т.п.) | SCM API в продукте — HTTP REST; лишняя сложность |

## Последствия

### Позитивные

- Один контур HTTP для всех SCM-адаптеров.
- Меньше жёсткой привязки к вендорским SDK.
- Retry и массовые политики не смешиваются с низкоуровневым клиентом.

### Негативные

- Больше своего кода на старте (обёртка, адаптеры).
- Не получаем «бесплатно» типы и методы из официальных SDK — пишем или генерируем
  под контракт платформы в адаптерах.

### Компромиссы

- Для одной платформы официальный SDK мог бы ускорить старт; сознательно меняем на
  единую обёртку ради нескольких SCM.
- Позже в отдельный адаптер можно обернуть вызовы SDK, если это не ломает общий
  контур — не предмет этого ADR.
