# ADR-26112801: Ранняя клиентская фильтрация до обогащения SCM-отбора

## Статус

✅ **Принято**

## Контекст

[Единый отбор][repository-selection] получает кандидатов листингом SCM, затем
дозагружает поля карточки и отбирает цели в процессе Git Herder
([ADR-26102001][adr-local-eval], [ADR-26102201][adr-hub]).

Раскладка документов listing / enrichment / enumeration
([ADR-26102201][adr-hub]) ранее совпадала с **порядком исполнения**: сначала
дозагрузить поля **всех** карточек list, потом применить клиентские
критерии. Для критериев по полям, которые list уже заполнил окончательно
(путь и имя на GitLab, теги GitHub из ответа Search), это даёт лишние
HTTP-вызовы: дозагрузка идёт по широкому набору, а сужение — только после
неё.

Аналитический критерий «есть ветка с именем» усиливает эффект: проверка
идёт **на каждую** карточку оставшегося набора. На GitLab путь и имя
оцениваются только на клиенте, поэтому дозагрузка веток без предварительного
отсева обходит все проекты list.

[ADR-26102001][adr-local-eval] допускает дополнительные вызовы API на
репозиторий для аналитических критериев и не фиксирует, что дозагрузка обязана
идти раньше дешёвой локальной проверки уже готовых полей.

## Решение

В режиме переносимых критериев (не `--scm-search`) после **полного**
завершения листинга порядок такой:

1. **Ранняя клиентская фильтрация.** Применить критерии, которые читают только
   поля карточки, уже окончательные после list: для поля нет **активного**
   задания дозагрузки. Активные задания — реестр дозагрузок текущего
   `upstream` после резолва параметров отбора.
2. **Обогащение.** Дозагрузить поля **только** у карточек, прошедших шаг 1.
   Пара «карточка × задание» и повторы — как раньше (очередь повторов прогона).
3. **Поздняя клиентская фильтрация.** Применить оставшиеся клиентские критерии
   (поля, которые шаг 2 только что записал). Сетевых запросов на этом шаге
   нет.

Композиция критериев не меняется: карточка в итоговом наборе, только если
прошла **оба** прохода (логическое И). Ветка `--scm-search` по-прежнему
отдельная: один листинг, без этих трёх шагов.

Какие критерии попадают в шаг 1 или 3, следует из реестра дозагрузок и
реестра клиентской фильтрации выбранного `upstream`, а не из отдельного
перечня имён флагов в этом ADR.

## Аргументация

| Альтернатива | Почему не выбрана |
| ------------ | ----------------- |
| Дозагрузить все карточки list, затем фильтровать | Лишний HTTP на карточки, которые дешёвый клиентский критерий всё равно отбросит; на больших GitLab-наборах критерий «есть ветка» становится непрактичным |
| Перенести путь и имя GitLab в server-side list | Ломает переносимую семантику шаблонов ([ADR-26102001][adr-local-eval]) |
| Оставить порядок «дозагрузка → фильтр» только для аналитических критериев | Дублирует два контура оркестрации без выигрыша: правило «поле уже окончательно» покрывает и метаданные, и ветки |

## Последствия

### Позитивные

- Дозагрузка (ветки, атрибуты, теги GitLab) идёт по уже суженному набору,
  когда пользователь задал путь или имя.
- Один алгоритм для всех `upstream`: не нужен особый пайплайн «только для
  веток».

### Негативные

- Два прохода клиентской фильтрации вместо одного; реализация должна не
  смешивать критерии, чьи поля ещё заменит дозагрузка.
- Процесс в ArchiMate-модели может отставать от этого порядка, пока в модель
  не добавят шаг ранней фильтрации; прикладной контракт оркестрации —
  спецификация загрузки из SCM, не этот ADR.

### Компромиссы

- Если из критериев отбора активны только те, что требуют дозагрузки, шаг 1
  пустой: дозагрузка по-прежнему по всему list. Сужение тогда — `--qp` /
  `--qn` или server-side фрагменты Search на GitHub, не этот ADR.
- Сбой дозагрузки конкретной карточки и его влияние на набор целей — не
  здесь; это контракт критерия и `--on-error`.
