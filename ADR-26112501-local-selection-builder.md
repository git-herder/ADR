# ADR-26112501: Билдер критериев локального отбора вместо колбэка

## Статус

✅ **Принято**

## Контекст

[Архитектурная модель](../documentation/architecture/git-herder.archimate)
описывает компонент **GitWorkingCopiesResolver** как приёмник каталога
`--workspace` и **колбэка** фильтрации. Функция
«Применение callback-фильтра» (`id-c4dfb8c0…`) на вход получает рабочую копию и
возвращает `true/false`; то, что осталось, резолвер возвращает вызвавшему.

Этот колбэк вынуждает каждую команду, вызывающую резолвер, **саму** знать детали
работы с `git` через **GitCliRunner**:

- `sync` читает `HEAD` и проверяет, что это `refs/heads/<branch>`
  (отбор «копия на ветке»);
- `merge` зовёт `git rev-parse --verify refs/heads/<from>` (отбор «есть ветка»);
- `publish` читает ремоты и сверяет хост (отбор «ремот не на этот SCM»).

Таким образом резолвер, заявленный как «не запускает `git`», фактически
делегирует фильтрацию наружу, а git-логика отбора просачивается в потоки команд.
Это нарушение единой ответственности и инкапсуляции: команда знает и **что**
отбирать, и **как** проверять через `git`.

Эпик «Аналитические критерии отбора по веткам» добавляет в локальный контур три
новых критерия — наличие ветки, расхождение веток, копия на ветке, — и часть из
них уже существует как колбэк-логика в `sync` и `merge`. Колбэк не позволяет
выразить новые критерии единообразно без повторного просачивания git-деталей в
каждую команду.

Ограничения:

- `git` запускается внешним процессом с машины пользователя
  ([ADR-26101702][adr-host-git]); библиотек go-git продукт не использует.
- Прокси-команды (`pull`, `push`, `fetch`, `remote`) не задают критериев отбора
  сегодня и не должны их получить как побочный эффект рефакторинга.
- Колбэк **RetryingQueue** (`id-e46eecf7…`) — отдельный механизм
  (обработчик элемента очереди) и **не** затрагивается этим решением.

## Решение

Заменить колбэк фильтрации **декларативным билдером критериев
локального отбора** с текучим (fluent) API. Билдер накапливает критерии и сам
исполняет их через **GitCliRunner**; вызывающие команды описывают **что**
отбирать, не зная, какие вызовы `git` и как устроен обход каталогов.

### Контур компонентов

Вводится новый компонент архитектуры **WorkingCopySelectionBuilder**:

- билдер **владеет** знанием `git` для проверки критериев (через GitCliRunner);
- билдер вызывает **GitWorkingCopiesResolver** для обхода каталога и
  сопоставления `--qp`/`--qn`;
- резолвер **перестаёт** принимать колбэк и **не запускает** `git` — как и
  заявлено в его контракте;
- `--interactive` применяется **после** критериев билдера, как сегодня после
  колбэка.

Канон трассировки «компонент → пакет» — в
[ADR-26110801][adr-layout] (пакет `internal/workspace`, файл `select.go`).

### Вид API

```go
WorkingCopySelectionBuilder.
    Name(qn...).
    Path(qp...).
    HasBranch("develop").
    Differs("develop", "main").
    OnBranch("develop").
    Interactive(true).
    Find(ctx)
```

Каждый метод накапливает критерий как замыкание и возвращает билдер; `Find`
запускает обход, критерии и интерактив, возвращая итоговый список копий.

### Покрытие существующих отборов

| Отбор (ныне колбэк) | Критерий билдера |
| ------------------- | ---------------- |
| `sync`: копия на ветке `<branch>` | `OnBranch(branch)` |
| `merge`: есть ветка `<from>` | `HasBranch(from)` |
| `publish`: ремот не на заданный SCM-хост | критерий ремота (имя уточняется в спецификации) |

Новые критерии эпика — `HasBranch`, `Differs`, `OnBranch` — задаются тем же
билдером в локальном контуре.

### Отличие от Builder-паттерна SCM-контура

Билдер SCM-контура (`ScmListingBuilder`, `ScmEnrichmentBuilder`) разделяет фазу
сборки и исполнения: `Build()` возвращает runtime-интерфейс `ScmListing`
([ADR-26110801][adr-layout]). **Здесь** билдер сам и накапливает критерии, и
исполняет `git` — разведение `Build()` → отдельный runtime-интерфейс было бы
искусственной надстройкой над одной фазой. Это осознанное расхождение.

## Аргументация

| Альтернатива | Почему не выбрана |
| ------------ | ----------------- |
| Критерии-структуры + интерфейс-исполнитель (диспетчер по типу) | Критерий становится значением-данными, но вводит «критерий-бог»: единый исполнитель с растущим `switch` по типам; диспетчеризация дублирует знание о каждом критерии в одной точке; ради общности вводится лишний слой над одной фазой исполнения |
| DSL-строки (`"has-branch:develop"`, `"diff:develop..main"`) | Максимально развязывает команды, но переносит проверку корректности в рантайм; контракт превращается в грамматику, которую надо синхронно править в парсере, исполнителе, справке CLI и обработке ошибок; слабая типизация, ошибки выявляются поздно |
| Оставить колбэк, расширять новыми колбэками | Не решает исходную проблему: git-логика остаётся в командах; каждый новый критерий эпика требует новой колбэк-логики в каждом вызывающем; инкапсуляция не восстанавливается |
| Вынести git-проверки в резолвер без билдера (методы на резолвере) | Резолвер перестаёт быть «поиском копий» и становится контейнером всех git-проверок; смешиваются две ответственности (обход и фильтрация) в одном компоненте; труднее тестировать команды без подмены резолвера целиком |

## Последствия

### Позитивные

- Команды `sync`, `merge`, `publish` перестают напрямую вызывать `git`
  для отбора; git-логика инкапсулирована в билдере.
- Новые критерии эпика (наличие ветки, расхождение, копия на ветке) задаются
  единообразно через билдер, без новой колбэк-логики в каждой команде.
- Билдер — единственная точка знания о том, какие вызовы `git` проверяют каждый
  критерий; замена `GitCliRunner` на фейк в тестах команды тривиальна.
- Резолвер возвращается к заявленной ответственности: обход и `--qp`/`--qn`,
  без запуска `git`.

### Негативные

- Композиция критериев из YAML-профиля требует явного маппинга «ключ профиля →
  метод билдера» в каждой команде: билдер не принимает критерий как данные, как
  у варианта со структурами. Это осознанная цена выбранного варианта.
- Билдер постепенно становится реестром всех git-проверок (`HasTag`, `IsDirty`,
  `AheadOf`…); рост нужно контролировать, чтобы не превратить его в
  «билдер-бог».
- Команды нужно рефакторить с сохранением продуктового эффекта (reconcile
  текущих сценариев `sync`/`merge`/`publish`).

### Компромиссы

- Билдер и резолвер живут в **одном** пакете `internal/workspace` (правило «один
  механизм — один пакет»), но это **два** компонента архитектуры; канон —
  таблица в [ADR-26110801][adr-layout].
- Прокси-команды остаются без критериев; их поток не меняется.
- Форма API (имена методов, сигнатуры, обработка ошибок `git`) уточняется
  в спецификации `git-working-copies-resolver.md` после этого ADR; здесь
  зафиксирован только выбор паттерна — билдер, а не колбэк и не DSL.
