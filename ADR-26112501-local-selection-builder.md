# ADR-26112501: Декларативный API критериев локального отбора вместо колбэка

## Статус

✅ **Принято**

## Контекст

[Архитектурная модель](../documentation/architecture/git-herder.archimate)
описывает компонент **GitWorkingCopiesResolver** как приёмник каталога
`--workspace` и **колбэка** фильтрации. Функция
«Применение callback-фильтра» (`id-c4dfb8c004324ae681c2c614ac2448ab`) на вход
получает рабочую копию и возвращает `true/false`; то, что осталось, резолвер
возвращает вызвавшему.

Этот колбэк вынуждает каждую команду, вызывающую резолвер, **саму** знать детали
работы с `git` через **GitCliRunner**:

- `sync` читает `HEAD` и проверяет, что это `refs/heads/<branch>`
  (отбор «копия на ветке»);
- `merge` зовёт `git rev-parse --verify refs/heads/<from>` (отбор «есть ветка»);
- `switch` без `--create`/`--force-create` зовёт тот же
  `git rev-parse --verify refs/heads/<branch>` (отбор «есть ветка»);
- `publish` читает ремоты и сверяет хост (отбор «ремот не на этот SCM»).

Таким образом резолвер, заявленный как «не запускает `git`», фактически
делегирует фильтрацию наружу, а git-логика отбора просачивается в потоки команд.
Это нарушение инкапсуляции: команда знает и **что** отбирать, и **как**
проверять через `git`.

[Единый отбор для массовых операций][repository-selection] требует одной модели
локального отбора для всех команд над копиями. Критерии наличия ветки и «копия
на ветке» уже существуют как колбэк-логика в `sync` и `merge`. Колбэк не
позволяет выразить их единообразно без повторного просачивания git-деталей в
каждую команду.

Ограничения:

- `git` запускается внешним процессом с машины пользователя
  ([ADR-26101702][adr-host-git]); библиотек go-git продукт не использует.
- Прокси-команды (`pull`, `push`, `fetch`, `remote`) не задают критериев отбора
  сегодня и не должны их получить как побочный эффект рефакторинга.
- Колбэк **RetryingQueue** (`id-e46eecf7…`) — отдельный механизм
  (обработчик элемента очереди) и **не** затрагивается этим решением.

## Решение

Заменить колбэк фильтрации **декларативным текучим (fluent) API** на самом
**GitWorkingCopiesResolver**. Отдельный компонент для сборки критериев не
вводится. Резолвер накапливает условия своими методами и сам исполняет критерии
через **GitCliRunner**; вызывающие команды описывают **что** отбирать, не зная,
какие вызовы `git` и как устроен обход каталогов.

### Контур

Носитель API — существующий **GitWorkingCopiesResolver**:

- точка входа — `Resolve()` без аргументов; она возвращает резолвер;
- каталог, `--qp`/`--qn`, критерии и `--interactive` задаются методами
  резолвера, а не аргументами одного вызова и не колбэком;
- резолвер **владеет** знанием `git` для проверки критериев и исполняет их
  через **GitCliRunner**; обход каталога и сопоставление `--qp`/`--qn` остаются
  его ответственностью и `git` не запускают;
- `Find` запускает обход, критерии и интерактив и возвращает итоговый список;
- `--interactive` применяется **после** критериев, как сегодня после колбэка.

Канон трассировки «компонент → пакет» не меняется:
[ADR-26110801][adr-layout], пакет `internal/workspace`, файл `resolve.go`.

### Вид API

```go
workspace.Resolve().
    Workspace(absPath).
    Path(qp...).
    Name(qn...).
    HasBranch("develop").
    OnBranch("develop").
    NoRemoteOnHost(host).
    Interactive(true).
    Find(ctx)
```

Каждый метод накапливает условие и возвращает тот же резолвер. `Path` и `Name`
задают шаг пути и имени, а не критерий. `Find` запускает обход, критерии и
интерактив, возвращая итоговый список копий.

### Покрытие существующих отборов

| Отбор (ныне колбэк) | Метод резолвера |
| ------------------- | --------------- |
| `sync`: копия на ветке `<branch>` | `OnBranch(branch)` |
| `merge`: есть ветка `<from>` | `HasBranch(from)` |
| `switch`: без `--create`/`--force-create` есть ветка `<branch>` | `HasBranch(branch)` |
| `publish`: ремот не на заданный SCM-хост | `NoRemoteOnHost(host)` |

Имена методов, сигнатуры и обработка ошибок `git` — в спецификации
`git-working-copies-resolver.md`. Новые критерии того же локального контура
добавляются методами этого резолвера, а не колбэком команды.

### Отличие от Builder-паттерна SCM-контура

Билдер SCM-контура (`ScmListingBuilder`, `ScmEnrichmentBuilder`) разделяет фазу
сборки и исполнения: `Build()` возвращает runtime-интерфейс `ScmListing`
([ADR-26110801][adr-layout]). **Здесь** отдельного компонента-билдера нет:
резолвер сам накапливает условия и сам исполняет `git`. Разведение `Build()` →
отдельный runtime-интерфейс было бы искусственной надстройкой над одной фазой.
Это осознанное расхождение.

## Аргументация

| Альтернатива | Почему не выбрана |
| ------------ | ----------------- |
| Отдельный компонент-билдер, который вызывает резолвер | Дробит один механизм на два компонента. Обход без критериев не является самостоятельной фазой |
| Критерии-структуры + интерфейс-исполнитель (диспетчер по типу) | Вводит «критерий-бог»: единый исполнитель с растущим `switch` по типам и лишний слой над одной фазой |
| DSL-строки (`"has-branch:develop"`) | Проверка корректности уезжает в рантайм; контракт становится грамматикой, ошибки выявляются поздно |
| Оставить колбэк, расширять новыми колбэками | Git-логика остаётся в командах; каждый новый критерий снова требует колбэк в каждом вызывающем |
| Методы-проверки на резолвере без текучей сборки | Вход остаётся списком разнородных аргументов. Команда не собирает отбор как набор именованных условий |

## Последствия

### Позитивные

- Команды `sync`, `merge`, `switch`, `publish` перестают напрямую вызывать `git`
  для отбора; git-логика критериев инкапсулирована в резолвере.
- Критерии локального контура задаются единообразно методами резолвера,
  без новой колбэк-логики в каждой команде.
- Резолвер — единственная точка знания о том, какие вызовы `git` проверяют
  каждый критерий; замена `GitCliRunner` на фейк в тестах команды тривиальна.
- Отдельный компонент архитектуры и новая строка «компонент → пакет» не нужны.

### Негативные

- Композиция критериев из YAML-профиля требует явного маппинга «ключ профиля →
  метод резолвера» в каждой команде: резолвер не принимает критерий как данные,
  как у варианта со структурами. Это осознанная цена выбранного варианта.
- Резолвер постепенно становится реестром всех git-проверок отбора (`HasTag`,
  `IsDirty`, `AheadOf`…); рост методов нужно контролировать, чтобы не превратить
  его в контейнер любых проверок копии.
- Команды нужно рефакторить с сохранением продуктового эффекта (reconcile
  текущих сценариев `sync`/`merge`/`switch`/`publish`).

### Компромиссы

- Резолвер остаётся одним компонентом и одним пакетом `internal/workspace`.
  Он и обходит каталог, и исполняет критерии: это одна фаза отбора, а не две
  ответственности, требующие разных компонентов.
- Прокси-команды остаются без критериев; их поток не меняется.
- Форма API (имена методов, сигнатуры, обработка ошибок `git`) уточняется
  в спецификации `git-working-copies-resolver.md`; здесь зафиксирован выбор
  паттерна — текучий API резолвера, а не колбэк, не DSL и не отдельный билдер.
- `Log` и `Picker` — журнал вывода `git` и источник списка, не колбэк отбора.
  Копию они не принимают и не отбрасывают.
